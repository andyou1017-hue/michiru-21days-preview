## 新規に明確化した同期上のリスク：削除した記録が別端末から復活し得る

コード経路：`runtime/gateway.js` の `POST /api/entries/delete-all` は `entries` を物理削除する。一方、`app/js/store.js` の `mergeRemote(remoteEntries)` は、サーバーに日別記録が存在しないときでも端末側に旧記録があれば `pendingRemote[d]` に入れ、`pushRemote()` が `POST /api/entry` で再アップロードする。アプリ起動時の `app/js/app.js` からも `mergeRemote(res.entries)` が呼ばれる。

再現可能な論理シナリオ（**今回、実端末・自動テストでの再現は未実施**）：

1. 同じ受講生が端末A・BでDay 1の記録を保持する。
2. 端末Aで「すべての記録を削除」し、サーバーから当該記録が消える。
3. 端末Bが古い端末内データを持ったまま起動・同期する。
4. サーバーが空でも、Bの旧記録が「未送信」とみなされ再アップロードされ得る。

これは記録の意図しない復活に関わるため、**複数端末の削除同期を配布合格に含めない**。修正案は、サーバー側の削除墓標または単調増加リビジョンを使い、更新と削除の順序をサーバーで判定すること。端末時計の文字列比較だけに依存しない。古いバックアップからの復元、オフライン後の再接続、端末A/Bの同時編集も含めて回帰テストを先に定義する。端末内だけの未同期記録を無断で破棄しない。
